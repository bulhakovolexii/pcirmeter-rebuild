# Перетворення AD → температура

Статус: v1 (2026-10-22). Джерело: Ghidra-аналіз `FPGA_CalcTemp_List.dll`
(`getSpotTemp` → `FUN_10005390`; LUT `FUN_10004b00`; τ `FUN_100012e0`, `FUN_100013c0`, `FUN_10001510`;
параметри `FUN_10002470`). Еталонна реалізація для досліджень: `tools/irtemp.py`;
реалізація в ядрі: `src/core/temperature.ts` (звіряється з `irtemp.py` фікстурами `tests/fixtures/temperature/`).
Константи атмосферних таблиць: `tools/atmosphere_tables.json`.

Усі вхідні дані беруться **з самого файлу** (заголовок ІЧ-блоку, див. `file-format.md`) —
жодних калібрувальних файлів камери не потрібно.

## Алгоритм

Позначення: K = 273,15; ε, d, T_atm, RH, T_refl, offset — параметри з заголовка або змінені користувачем.

1. **Корекція затвора:** `a = AD + ΔAD`, де ΔAD — поле 0x5C (`u16 − 10000`).
   Якщо поле нульове, ΔAD обчислюється з температури затвора (0x54) зворотним пошуком у таблиці —
   **[г: деталі не відновлено, у всіх зразках поле заповнене]**.
2. **Калібрувальна таблиця:** кусково-лінійна інтерполяція `T_lut(a)` за вузлами (AD_i, T_i).
   Якщо `a` поза [AD_0, AD_{N−1}] — помилка «поза діапазоном» (оригінал повертає ±4001).
3. **Поправка калібрування:** `T_bb = (0,95·(T_lut+K)⁴ + 0,05·298,15⁴)^¼ − K`.
4. **Пропускання атмосфери τ:**
   - `ρ = VAPOR[clamp(trunc(T_atm + 49), 0, 98)]` — густина насиченої пари, г/м³ (таблиця на 99 значень, −49…+49 °C);
   - `w = ρ · RH · d / 1000` (мм осадженої води);
   - `τ = interp(w; TAU_H2O) · interp(d/1000; TAU_DIST)`, сітка x = {0; 0,2; 0,5; 1; 2; 5; 10; 20; 50; 100; 200},
     лінійна інтерполяція, x ≥ 200 → останнє значення.
5. **Радіометричне рівняння (закон Стефана–Больцмана, ступінь 4):**
   ```
   W = (T_bb+K)⁴ / (ε·τ)  −  (1−ε)·(T_refl+K)⁴ / ε  −  (1−τ)·(T_atm+K)⁴ / (ε·τ)
   T = W^¼ − K + offset
   ```
   W < 0 → помилка; T < −60 або T > 4000 → помилка. У ядрі всі «помилки» — `NaN`.
6. **У .NET-шарі:** результат обмежується зверху `maxRange` (150 або 400 °C за Temp_Range) і переводиться
   в одиниці: °F = °C·1,8 + 32; K = °C + 273,15. Знизу не обмежується (`AnalyzeHead_ListVer.ADToTemp`).
   Ядро повертає необмежене значення; межі — `measurementRange(Temp_Range)`.
   **Рішення вебверсії (погоджено з викладачем):** показувати справжнє значення з позначкою «поза діапазоном»,
   а не обрізати його, як оригінал.

**Продуктивність [п]:** результат залежить лише від цілого AD, тож кадр перераховується через таблицю
на діапазон [min AD, max AD] кадру (`frameTemperatures`): 384×288 — ≈ 0,3 мс у Node.

## Обчислення для об'єктів аналізу (як в оригіналі)

Інтерфейс оригіналу (`PCIRMeter.IRImageBox`) рахує все **в °C (float32) по пікселях елемента керування на екрані**,
а не по пікселях кадру. ІЧ-кадр розтягнуто на елемент керування з неціловим масштабом
`zoomX = ширина_елемента / W`, `zoomY = висота_елемента / H`; екранна точка (x, y) → піксель кадру
`(int(x / zoomX), int(y / zoomY))`. **[п]** (код + звірка частини Б, див. нижче)

- **Точка:** один піксель кадру, `ADToTemp(AD)` (з обрізанням зверху 150/400 °C).
- **Прямокутник** (`GetAllPointsOfNormalRect`, `GetMaxMinParametersOfNormalRect`): усі екранні пікселі
  `x ∈ [x₀, x₀ + w)`, `y ∈ [y₀, y₀ + h)` (права й нижня межі не входять); для кожного — °C відповідного пікселя кадру.
  Max/min — по цих значеннях; **середнє = Σ T / (w·h)**, тобто кожен піксель кадру зважено кількістю екранних пікселів,
  що на нього припали (на краях — менше). Результат залежить від розміру вікна програми.
- **Лінія** (`GetAllPointsOfSingleLine`, `GetTemperatureOfSingleLine`): крок по екранних пікселях уздовж більшої
  з осей, від початку до кінця **без кінцевої точки** (вертикальна в межах одного стовпця кадру — з кінцевою),
  друга координата `int((k − k₀)·нахил + c₀)`; точки, що потрапили в уже бачений піксель кадру, відкидаються.
  Max/min/середнє (рівновагове) — по °C унікальних пікселів кадру; вони ж — точки графіка профілю.
- `IrMeter.AnalyzeHead_ListVer.Rectangleobj` (max/min/середнє по AD, середнє = `ADToTemp(Σ AD / n)`) в інтерфейсі
  **не викликається**; попередня версія цієї специфікації помилково спиралася на нього.

**Рішення для вебверсії (погоджено з викладачем 2026-10-22, реалізація — I-11):** рахувати по пікселях кадру, а не екрана: прямокутник — цілі пікселі кадру,
середнє — рівновагове по °C; лінія — піксельна лінія в координатах кадру (див. I-11). Результат тоді не залежить
від розміру вікна; від оригіналу відрізняється лише вагами крайніх пікселів — на еталонах ≤ 0,15 °C (F1, масштаб 6,2;
F5/F7 ≤ 0,01 °C). Для тестів сумісності модель оригіналу відтворено в `tools/fit_objects.py`.

## Поведінка оригіналу, виявлена еталонами [п]

- **Межі шкали (автоматичний режим)** = `T(FPGA_Level + FPGA_Span)` і `T(FPGA_Level)` з поточними параметрами об'єкта
  (`IRControl1`, `defaultLevelSpan`), а не екстремуми кадру.
- **Мітки Max/Min кадру** (`IRImageBox.SetParameters_IrImage`): пошук по °C починається з max = 0 і min = 1000.
  Тому для кадру, де всі температури від'ємні, оригінал показує **Max = 0,0** (F3 при ε 0,70: справжній max −1,6 °C).
  Це помилка оригіналу; у вебверсії показувати справжній максимум (тест на сумісність — з урахуванням цієї поведінки).
- **Аварійне завершення при межі шкали < −1 °C** (`IRControl1.setmaxandminnum`): допоміжним полям ізотерм
  присвоюється −1, що виходить за їхній діапазон → `ArgumentOutOfRangeException`. На F3 (ε 0,98, RH 50 %)
  поріг — d = 930,9 м; наша формула дає межу шкали −1,00 °C саме при 930,9 м — незалежне підтвердження τ на великих відстанях.
  У вебверсії такого обмеження немає.

## Відкриті питання
- Обчислення ΔAD з температури затвора, коли поле 0x5C = 0 (`FUN_10004580`, тіло обрізане декомпілятором).
- Роль поправки `+0x110` (дрейф між двома температурами затвора, `FUN_10004490`) — у `getSpotTemp` не використовується **[г]**.
- Точність float32 оригіналу проти float64 у нашій реалізації (очікувана різниця < 0,01 °C).
